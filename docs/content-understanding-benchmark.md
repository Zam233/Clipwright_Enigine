# 内容理解基准集与指标（R1–R10 汇总）

> 本文是 2026-09-14「让 Agent 知道自己剪的是什么」这条线的**基准集说明 + 指标汇总**。
> 计划与设计见 [content-understanding-plan-2026-09-14.md](content-understanding-plan-2026-09-14.md)。
>
> **一句话读法**：下面所有数字都是在**合成素材 / 自写夹具**上测出来的，
> 证明的是"链路正确、边界诚实"，**不是**"真实素材上的效果"。
> 每一项都附了必须一起读的「验证边界」。

---

## 1. 为什么要有这份文档

这条线一共 10 轮、9 个验收脚本。如果不汇总，会出现两个问题：

1. **数字漂移**：文档写 100%、脚本其实没跑过（或跑了但改过夹具）；
2. **数字被误读**：把"合成素材上 100%"当成"真实素材上也 100%"。

所以：

- 所有数字由 `scripts/verify_all_metrics.py` **一键复跑**，它只调用各轮脚本、不重复实现指标，
  文档数字与脚本输出是同一个来源；
- 每个指标都强制带一条「验证边界」，写清楚这个数字**不**代表什么。

```powershell
python scripts/verify_all_metrics.py            # 全部（含加载 CLIP 的慢脚本，约 5 分钟）
python scripts/verify_all_metrics.py --fast     # 跳过加载模型的脚本（约 10 秒）
python scripts/verify_all_metrics.py --only R7  # 只跑某一轮
python scripts/verify_all_metrics.py --json docs/content-metrics-latest.json
```

## 2b. 真实素材基准（Pexels，2026-09-14 补测）

R1–R10 的验收全在合成素材上，真实素材一直是"未验证"。下面是**真实拍摄片段**上的实测。

**怎么取数**：`scripts/fetch_pexels_testset.py`（key 只走环境变量 `PEXELS_API_KEY`，
不写进仓库；来源/作者/许可记在 `manifest.json`）。本次取 4 段（足球 / 海面 / 城市夜景 / 厨房），
640p、截取前 8 秒，共约 2.2MB。

**怎么测**：`scripts/benchmark_real_material.py`（三项各有明确真值）。

| 项 | 真值怎么来的 | 实测 |
|----|--------------|------|
| 镜头切分 | 把 4 段真实素材**拼接**成一条 32.3s 视频，拼接处即硬切（真值 8.08 / 16.155 / 24.235） | 默认阈值 **P=1.000 R=1.000 F1=1.000**（3/3 全中、0 虚检）；阈值 0.2 / 0.12 结果相同 |
| 中文检索 | 每条素材配 3 条中文查询（说法**刻意不同于**素材标签：素材标签"水面"、查询"海边的镜头"） | **top-1 = 12/12 = 100%**（随机基线 25%），top-3 = 100% |
| 管线贯通 | 真实索引上的问答 / 接地 / 一句话剪辑 | 问答：清单 2 命中、排序命中、运动过滤 2 命中、"有黑场吗"**如实 0 命中**（素材里确实没有）；剪辑：删除 32.3s→24.2s、全片段 1.5 倍速、"剪到 10 秒"→**精确 10.0s** |

**真实素材上的好消息（合成素材上测不出来的）**：

- **CLIP 零样本标签在真实画面上是像样的**：4 段素材分别给出"运动 / 夜景 / 食物 / 水面"，
  与内容对得上。对比 R2 在合成帧上得到"屏幕录制 / 左轮手枪"那种离谱结果——
  说明 R2 记录的"合成帧标签不可信"确实是**分布外**问题，不是模型坏了。
- **CLIP 画面检索的排序在真实素材上完全正确**：4 条中文查询（海边 / 球场 / 夜里城市街道 /
  做饭）全部把正确素材排在第一位。原始余弦：命中约 0.26–0.27，不相关约 0.14–0.24。

**真实素材暴露并修复的 3 个缺陷**（合成素材**全部没暴露**）：

1. **视觉检索被门槛整体吃掉（致命）**：`search_shots` 用"融合分 ≥ 0.05"当门槛，
   而 CLIP 视觉分的量级本来就小（真实素材命中 adj≈0.09 × `W_VISUAL` 0.5 = 0.044），
   于是**只有视觉命中的正确结果被全部过滤**——实测"找海边的镜头"返回 0 结果，
   尽管海浪镜头排第一。根因：绝对阈值套在"尺度随可用信号组合变化"的融合分上。
   修：三路信号各有自己的下限（关键词 >0 / 文本向量 ≥0.35 / 画面 ≥0.22），融合分只用于排序。
   合成基准没暴露，是因为它直接调 `sem.rank_shots(min_score=0)`，
   **从没走过 `search_shots` 的融合 + 门槛**。
2. **文本向量路静默死亡**：本机 `.env` 把嵌入 provider 指向 `openai/text-embedding-v4`
   配无效 key → 401 → 检索静默退化为"只剩视觉分"，表现是**所有查询 0 命中**。
   修：结果里回传 `degraded` 原因（"文本向量不可用 / 画面向量不可用"），
   让"门面挂了"和"素材里确实没有"能区分开。本组实测改用本地
   `BAAI/bge-small-zh-v1.5`（离线可用、512 维）。
3. **重复片段 id 会"删一个删一串"**：拼时间线时 id 生成规则撞车（素材名前 8 字符相同），
   三个片段同 id，于是"删掉第 2 个片段"把三个一起删了（4 → 1）。修：**执行前**检查重复 id 并告警
   （原先只在执行后的不变量检查里报，那时用户已经多删了）。

**真实素材上仍未解决的（如实）**：

- **自然剪辑点的真值只有"多方法一致"**：本环境的模型读不了图，无法像人类评审那样逐帧确认，
  所以判据是"ffmpeg scene / 帧间差尖峰 / 直方图跨度三种独立方法在同一时刻报切点"。
  这**不等于人工标注**；
- **交叉溶解补检有已知误报**：在 8 秒截取版的海浪片段上会误报 1 处（涌浪也是"持续的大幅变化"）。
  未截取的 45 秒海浪片段上没有误报——**误报依赖素材**，如实记录，并给了开关
  `content_index_gradual_detect` 可关；试过"转场前后应稳定"的判据，实测会把溶接尾部
  仍在变化的情况一起拒掉，所以没采用；
- 免费素材分布（低码率、多为单镜头）不代表真实拍摄素材；检索查询为人工标注（20 条），
  top-1 90% 是小样本结果；
- 1080p / 4K 素材的索引成本**没有实测**（只有 640×360 的 48ms/秒）。

### 2c. 真实素材补测后修掉的三项「仍未解决」

| 原来未解决 | 怎么修的 | 实测效果 |
|------------|----------|----------|
| `visual_description` 覆盖率 **0**（云端多模态默认关闭）→ 每段素材只有 1 个标签 → 方案接地 **0/2** | 新增 `services/content_describe.py`：用**已测到的字段**（明暗/景别/运镜/质量/标签/语音/音频事件）拼一句可检索中文描述。**零模型调用**，`evidence` 写明 `composed:stats+clip+audio`，置信度标 0.5（不冒充"模型级理解"） | 覆盖率 **0 → 1.0**；接地从 **0/2 → 2/2**（具体描述 2/2、泛描述也 2/2） |
| 切分只在拼接素材上验（Pexels 片段多为单镜头） | ① 补检**交叉溶解**（`detect_gradual_transitions`：直方图 L1 归一化 + 跨窗口跨度 + 持续性判据）；② 扩大素材到 8 段并找**自然剪辑点**；③ 拼接素材规模从 32s 提到 72s（4 段真实素材 → 3 处真值硬切） | 拼接切分 **P=R=F1=1.000**（3/3）；交叉溶解 **检出**（真值中心 12.32s → 检出 12.40s，ffmpeg 老路径**漏检**）；自然剪辑点被独立方法确认（类型：渐变） |
| 未测索引成本 | `benchmark_real_material.py` 新增成本项：真实像素拼 129s 长素材，**预热剔除模型加载**后再计时 | **48ms / 秒素材**（预热后 6.2s / 129s；首次含模型加载 21.3s）；按稳态外推 640×360 的 10 分钟 ≈ 0.5 分钟（**外推≠实测**，1080p 会更高） |

**这两项修复过程中又抓到的真问题**：

- **直方图归一化口径错误（真 bug）**：`cv2.normalize` 默认 **L2** 归一化，导致"交集"可以 >1、
  跨度出现**负值**（实测一处溶接的跨度是 **-0.92**，看着像"完全负相关"，实际是口径错了），
  溶接因此检不出来。必须 **L1**（和为 1）。已加回归用例。
- **"未测量 vs 测到 0"混淆**：`ShotStats` 默认值是 0，第一版对一条裸 `ShotRecord`
  合成出"偏暗的画面。"——纯属凭空捏造。改为以 `frame_count > 0` 判断"统计确实跑过"。
- **`fx_brightness` 等调色字段不在可修改白名单里**：这是生成人工评分表时暴露的——
  **"把画面调亮一点"解析不出任何操作**，而该字段在 `Clip` 上存在、渲染端也支持。
  已把 `fx_brightness/fx_contrast/fx_saturation/fx_blur/fx_hue` 加入白名单（值域与
  `schema/timeline.py` 对齐）并补常见说法（调亮/调暗/加对比度/鲜艳点/黑白/模糊/清晰），
  程度词分档（"亮一点" ×1.15 vs "亮很多" ×1.6）。

### 2d. 唯一仍然做不了的一项：主观评分

R10 的验收指标里有一条我**做不了**的："3 个项目，主观 ≥ 4/5 且改动可解释"。
主观评分必须由真人打，模型给自己打分不算数。所以本轮交付的是**工具**而非结果：

```powershell
# 1) 生成评分表（跑真实链路，产出 markdown + json）
python scripts/make_eval_sheet.py --dir data/pexels_real --out eval/eval_sheet.md
# 2) 人工在 markdown 里给 C1–C5 打 1–5 分并写理由
# 3) 汇总（会给出总体均分与是否达到 ≥4/5）
python scripts/make_eval_sheet.py --score eval/eval_sheet.json
```

评分项：C1 意图理解 / C2 改动正确 / C3 改动可解释 / C4 不过度改动 / C5 失败时诚实。
仓库里已附一份**未评分**的 `eval/eval_sheet.md`（5 个真实任务的意图、dry-run 预览、
实际结果都在表里，评审者不需要看代码就能判断）。

## 4. 每个数字的「验证边界」（必读）

| 轮 | 这个数字**不**代表 |
|----|--------------------|
| R1 | 只验证 L0 统计维度；L1–L3 的覆盖率在 R1 时如实显示为 0（后续轮次才补） |
| R2 | **合成帧上的 CLIP/ImageNet 标签不可信**：实测输出"屏幕录制""左轮手枪"这类明显无关结果（分布外失败）。真实拍摄素材的表现**未验证**；跨淡化/同色相邻切分漏检是方法学盲区 |
| R3 | 音频事件用**程序合成**的 wav；**未安装 STT 后端**，自动转写路径从未真正跑过 |
| R4 | 30 条问答是我手写的；当时的向量只覆盖**镜头文字**、覆盖不到像素（R9 才补上画面向量） |
| R5 | 50 条是我手写的常见说法，不是真实用户语料；**LLM 解析路径只有打桩测试** |
| R6 | 夹具自写；会话短名单只在**进程内存**；反问策略是阈值 + 规则，不是概率化澄清决策 |
| R7 | 合成时间线（无真实素材、无真实模型）；6 组案例的指令与期望值都是我写的 |
| R8 | 构造索引与场景；关键词/标签**规则检索** + R9 加的语义兜底；真实素材上的匹配质量未验证 |
| R9 | 基准是**合成画面**，测的是颜色/图案/明暗这类**画面属性**——这是合成帧能承载的语义上限；"这是不是一场足球赛"这类场景语义在合成帧上做不了。**真实素材召回率未验证** |

**跨轮次的共同欠账**（各轮文档里反复写过，这里集中列一次）：

1. **没有真实素材**：本会话开始就确认过拿不到真实拍摄素材，所有验收都是合成 + 自写夹具；
2. **云端多模态从未真实调用**：通道接通、默认关闭，只有打桩测试；
3. **没有 STT 后端**：`speech` 维度在真实运行时会是空的；
4. **前端未做真实浏览器验收**：确认卡等 UI 的测试是 jsdom + mock；
5. **规则类解析器（R5/R6）与中文词表（R9）覆盖的是常见说法**，长尾靠反问兜底；
6. **本机 OpenAI key 无效**（实测 401）：嵌入后端不可用时检索自动退化为关键词。
   R4/R9 用的是本地 bge 与 CLIP，所以"向量检索"这条路本身是通的，
   但**云端嵌入**这条路在本机跑不起来。
   → **已在修复轮次 141 处理**：`.env` 改成本地 `sentence_transformer` +
   `BAAI/bge-small-zh-v1.5`（实测 `embedding_used=True`、稳态检索 0.13s）；
   同时发现并修掉一个"配置错了变成很慢"的陷阱——重排器模型名非法时，
   旧实现在**每次检索**都先付 20 秒的 `sentence_transformers` 导入、再报错并静默退回，
   现在是毫秒级暴露 + 失败记录（第一次 23.2s → 0.006s，第二次 0.000s）。
   修复过程中还纠正了自身两处错误：失败记录必须**按配置键控**（全局布尔会把改好的配置
   一起锁死、并让测试互相污染），以及 **provider 绑定必须优先于"显式关闭"**。

## 5. 怎么在这个基础上继续做

1. **接入真实素材**（第一优先级）：`python scripts/demo_content_understanding.py --material <视频>`
   会在真实素材上跑完整链路（建索引 → 问答 → 接地 → 一句话剪辑），
   并**如实打印**每一步实际拿到了什么。有了真实素材再谈标定：
   `content_index_blurry_sharpness`、`VISUAL_BASELINE`、接地阈值 0.24 都是经验值；
2. **替换合成基准**：把 R2/R4/R9 的合成夹具换成标注过的真实片段，
   同一套脚本不用改（脚本只吃"素材 + 真值"）；
3. **补 STT 与云端多模态的真实调用**，把那两个维度的覆盖率从 0 变成实测值；
4. **实测索引成本**：在 10 分钟 1080p 素材上计时，验证"≤ 3 分钟 CPU"这条门槛；
5. **规模验证**：现在检索是穷举点积，镜头数上万时需要向量库索引（未测）；
6. **"结构 → 时间线一致性"的强校验**：R8 只把引用写进 `clip.metadata` 供回查，
   没有断言"时间线实际用的素材覆盖了方案引用的素材"。

## 1. 为什么要走 C（以及代价）

### 1.1 问题陈述

v1.5 的形态是「确定性骨架 + 调度层」：管线负责执行，supervisor 负责读账本、归因、按规则表选策略。这套东西能给出成本上界与逐字节可复现（A10），但它有一个结构性缺陷：

> **决策权与执行权分离**：真正干活的是写死的 6 阶段 DAG，能做判断的 supervisor 却不能改顺序、不能换工具、不能自己补一步「先去查一下素材到底在不在」。

结果是：所有"计划外"的情况都要靠人。用户在 v1.5 评审时提出的正是这一点——**既然有主 agent，为什么还要管线**。路线 C 的回答是：不要骨架了，让 agent 自己规划并直接调工具；管线降级为它手里的一件工具。

### 1.2 C 的代价（先写清楚，别事后惊讶）

| 代价 | 说明 | 缓解（本文 §7/§9） |
|---|---|---|
| 成本失去天然上界 | 自由 agent 会自己决定读几轮、查几遍；v1.5 的「6 阶段 = 6 次结构化调用」不再成立 | 四道硬闸（回合/工具调用数/token/墙钟）+ 预算熔断 + 每步成本可见 |
| 逐字节可复现失效 | 同输入不再必然同输出，A10 等价性验收方式作废 | `record/replay` + golden runs + 评测门槛（F9） |
| 测试基线大面积重写 | 现在 3385 条里很多是「阶段输入→输出」契约测试 | 分三层保留/重写，见 §9.2 |
| 账本语义变化 | `LedgerEntry.stage` 不再有稳定含义 | 账本改为 typed 事件流（F4），`stage` 变成可选的 `capability` 标签 |
| 调试成本上升 | 失败不再对应"某个阶段"，而是"某一步的某个决定" | 计划树 + 每步快照 + 事件流回放（F8/F11） |

### 1.3 不做什么（Non-goals）

1. **不做通用编码 agent**：只在「视频创作」域内规划与执行。
2. **不做跨项目长期记忆共享**：记忆边界按项目/Persona 划分。
3. **不自动对外发布**：上传素材到外部服务、发布成片，必须人工点。
4. **不追求"完全无人工"**：授权与审核点不减少，只从"阶段边界"挪到"工具调用边界"。

## 2. 目标

1. 用户给一句话需求，主 agent 能产出一份**可读的计划**（要做哪几步、每步用什么能力、预估成本与耗时），并在执行中自我修正。
2. agent 能**直接调用 49 个工具里的每一个**（按权限档），不再依赖写死的阶段。
3. 现有管线**降级为工具**（`run_pipeline`），可由 agent 在"常规套路"时一键调用——**C 不等于把管线删掉，而是把它变成可选快路径**。
4. 所有执行仍在同一套安全边界内：执行网关、预算闸、审计、人工授权。
5. 单个任务可被**中断、接管、续跑**，且副作用不重复。

## 3. 用户故事

| 编号 | 角色 | 故事 |
|---|---|---|
| US1 | 创作者 | 我给一句话，它先给我计划（3–6 步），我确认或改一句，它才开始花钱。 |
| US2 | 创作者 | 素材缺失时它自己发现「第 3 段没有可用的实拍」，然后改计划：换成占位图+动画，而不是失败退出。 |
| US3 | 创作者 | 我看见它在第 4 步卡了 6 分钟，能看到它在跑什么命令、花了多少钱，并且能一键停。 |
| US4 | 创作者 | 我关掉浏览器第二天回来，它还在跑/或已停在检查点，我能接着来。 |
| US5 | 运维/管理员 | 我能看到每个工具被调用了多少次、失败率、平均成本，并能给某些工具设权限档。 |

## 4. 术语

| 术语 | 定义 |
|---|---|
| **Task** | 一次用户需求的完整执行单元（含计划、事件、产物、成本） |
| **Plan** | 有序 Step 列表；可被 agent 在执行中修改（replan） |
| **Step** | 计划中的一步：调用某个 Capability（工具/Skill/管线） |
| **Capability** | 可被 agent 调用的能力：`tool` / `skill` / `pipeline` / `subagent` |
| **ToolCall** | 一次具体调用（含入参、出参、耗时、成本、风险等级、是否需授权） |
| **Event** | 追加式事件（计划变更/工具调用/授权/降级/产物/告警），Task 的唯一事实来源 |
| **Checkpoint** | 可在其中断/恢复的状态快照（含幂等键） |
| **Attempt** | 同一 Step 的第 n 次尝试（对应 v1.5 的 ledger attempt 语义） |

## 5. 架构总览

```
┌────────────────────────────── 主 Agent（Kernel）──────────────────────────────┐
│  plan ─► act ─► observe ─► reflect ─┐                                        │
│   ▲                                 │                                        │
│   └──────── replan ◄────────────────┘                                        │
│  记忆：工作记忆（当前计划/最近观察） + 项目记忆（Mongo） + RAG 知识库          │
└───────┬────────────────┬───────────────┬──────────────────┬─────────────────┘
        │                │               │                  │
   Tool Surface     Skill Surface    Pipeline(as tool)   Subagent Pool
   （49 工具分级）    （4 Skill）      （老 6 阶段）        （星型，并发上限）
        │                │               │                  │
        └────────────────┴───────┬───────┴──────────────────┘
                                 ▼
                    ┌──────── 统一执行与治理层 ────────┐
                    │ ExecutionGateway（shell/python）  │
                    │ 权限档 / 预算闸 / 审计 / 授权     │
                    │ 事件流（append-only）+ 检查点     │
                    └──────────────────────────────────┘
```

**关键分层原则**：Kernel 只做「想和选」，**不直接碰副作用**；一切副作用经治理层。这条不因 C 而放松。

## 6. 功能需求

### F1 任务内核（Agent Kernel）

- **循环**：`plan → act → observe → reflect`，每轮一个 Step；`reflect` 决定继续/改计划/收尾。
- **计划可读**：计划必须结构化（`steps[{id, capability, args_brief, why, est_cost_usd}]`），前端与 API 都能读。
- **自我修正**：允许 `replan`（插入/跳过/重排 Step），但每次 replan 必须写事件并给出理由。
- **收尾义务**：无论成功/超限/失败，都必须产出「结论 + 已完成产物 + 未完成原因」三件套。
- **上限**（可配置，不可关闭为空）：`max_turns`（默认 30）、`max_tool_calls`（默认 80）、`max_wall_sec`（默认 3600）。
- **验收**：`A1`（超限优雅收尾）、`A8`（能回答在干什么）。

### F2 工具面（Tool Surface）

> **这是 C 里工作量最大、最容易被低估的一块。** 现状：49 个工具里只有 4 个内置工具声明了 `agent_callable`，其余是管线内部程序化调用。C 的前提是"agent 能调每一个"，所以必须先把工具面做出来。

- **统一契约**：每个工具声明 `llm_schema`（名称/描述/入参/出参）、`permission_tier`、`dry_run` 支持与否、`idempotency`（是否安全重放）。
- **权限档**（四级）：
  | 档 | 含义 | 例子 | 谁可调 |
  |---|---|---|---|
  | `read` | 纯读、无副作用 | `list_dir`、`ffprobe`、`scene_detect` | agent 自主 |
  | `write_local` | 只写项目工作区 | `video_trim`、`subtitle_write`、`render` | agent 自主（可撤销） |
  | `costly` | 花钱或长耗时 | `generate_text_video`、`tts_synthesize`、`material_search(付费源)` | agent 自主但受预算闸 |
  | `dangerous` | 可破坏/外泄/系统级 | `run_shell`、`run_python`、任何上传到外网 | **必须走授权门**（两级确认） |
- **幂等键**：每个 ToolCall 带 `idem_key = hash(step_id, attempt, tool, args)`；重放命中则复用结果不重复副作用。
- **dry-run**：`write_local`/`costly` 档必须支持 dry-run（返回"会做什么"而不做），供计划确认阶段用。
- **验收**：`A4`（权限档生效）、`A7`（能力覆盖 ≥90%）。

### F3 能力面：Skill 与管线降级

- **Skill**：4 个现有 Skill（`analyze_video_structure` / `generate_captions` / `analyze_audio_rhythm` / `dub_script`）纳入 Capability，schema 与工具同构。
- **管线降级为工具**：`run_pipeline(topic, persona_id, category_plugin_id, ...)` → 内部仍走现有 6 阶段，返回成片 + 摘要。agent 在"常规套路/预算敏感"时应优先选它（写入系统提示的策略偏好，而非硬编码）。
- **选择权在 agent**：不硬性规定"必须先试管线"；但**成本对比数据要可见**（F5），让偏好可被数据纠正。
- **验收**：`A9`（老 API 兼容）、`A10`（质量不下降）。

### F4 事件流与账本重定义

- **单一事实来源**：Task 的账本是 append-only 事件流（Mongo + 内存热层），事件类型固定：
  `task_start / plan / replan / step_start / tool_call / tool_result / approval_request / approval_result / degradation / artifact / step_end / task_end`。
- **`stage` 变成标签**：旧 `LedgerEntry.stage` 保留为可选字段（`capability` 现在承担语义），归因规则从「按 stage」改为「按 capability + 失败类别」。
- **兼容读**：`GET /api/pipeline/{pid}/ledger` 仍返回旧形状（翻译层），避免前端与外部脚本立刻断裂。
- **验收**：`A3`（每次调用都有审计）、`A8`。

### F5 预算与四道闸

| 闸 | 默认 | 触发行为 |
|---|---|---|
| 回合数 | 30 | 停止新 Step，进入收尾 |
| 工具调用数 | 80 | 同上 |
| token / 金额 | 沿用 `pipeline_budget_usd`（未配置=无上限，v1.5 语义不变） | 达 70% 收窄到 cheap 档；100% 停止新调用并收尾 |
| 墙钟 | 3600s | 硬停 + 落检查点 |

- **每一步都记账**：ToolCall 落 token/金额/耗时，前端与 API 实时可读。
- **超限必须体面**：产出「已完成到哪、还差什么、下一步建议」；不允许静默返回半成品。
- **验收**：`A1`、`A5`。

### F6 安全与授权

- **复用 v1.5 的执行网关**（`supervisor/gateway.py`）：硬底线 → 棘轮 → 独立 LLM 判定 → `max()` → 分流（low 直跑 / med 自动模式可免 / high 一次确认 / critical 两级确认）。
- **新增工具级门槛**：`dangerous` 档工具（包括任何"把本地文件发到外部"的能力）**不经过 LLM 也一律要授权**——因为这类工具的风险是结构性的，不是措辞问题。
- **不可绕过的五条红线**（C 版本）：
  1. 一切副作用经治理层，Kernel 不得直接 `subprocess`/写文件（测试卡死）；
  2. LLM 可见工具 ⊆ 白名单（`ToolRegistry` 声明的 `agent_callable` + 权限档）；
  3. 四道闸可配但**不可关闭为空**（配置校验拒绝 0/None）；
  4. 审计不可关闭；
  5. `dangerous` 档与不可逆操作必须人工确认（critical 两级）。
- **验收**：`A3`、`A4`、`A12`。

### F7 上下文与记忆

- **两类记忆**：工作记忆（当前计划 + 最近 N 条观察，滚动窗口）+ 项目记忆（Mongo：该项目历史决策/失败原因/用户偏好，按需检索）。
- **压缩策略**：观察到一定长度后做「摘要 + 结构化提取」（保留工具名、路径、数值），不允许把全量工具输出塞回上下文。
- **RAG**：复用现有 RAG 知识库给 Persona 风格与素材语义检索；检索结果**必须标注来源**，不得无源引用。
- **验收**：`A11`（长任务不因上下文超限失败）。

### F8 检查点与可恢复

- **检查点时机**：每个 Step 结束、每次授权决定后、每次墙钟即将超限前。
- **恢复语义**：`resume(task_id)` 从最近检查点继续；已完成的 Step 不重跑（靠幂等键与 Step 状态）。
- **人工接管**：任何时刻可 `pause`（停止发起新调用）、可 `inject`（人工插一句指令或改一步计划）。
- **验收**：`A6`（kill -9 后续跑不重复副作用）。

### F9 可复现、录制与评测

- **record/replay**：录制一次 Task 的「工具入参 + 出参 + 模型响应」；replay 模式下模型与工具都不真跑，用录制结果驱动。
- **golden runs**：10 个代表性选题（知识区长片/鬼畜快剪/数码评测/Vlog）作为回归基线，比较产物结构（timeline JSON 归一化）与关键指标（时长/轨道数/字幕条数/成本/耗时）。
- **评测门槛**：合并前必须过 `golden runs` 的结构一致性 + 人工抽检质量不下降。
- **验收**：`A2`、`A10`。

### F10 多代理

- **沿用 v1.5 语义**：星型拓扑（子代理不得再派生）、并发上限 `max_concurrent_subagents`、子代理开销单独入账。
- **分工建议**：主 agent 只做规划与验收；具体探查（"这个素材到底能不能用"）派给只读子代理；写操作尽量留主 agent（减少并发写冲突）。
- **验收**：`A12`。

### F11 可观测与前端

- **计划视图**（新）：当前计划 + 每步状态（待办/进行/完成/失败/跳过）+ 每步成本与耗时 + replan 历史。
- **调用流**（改造现有执行日志）：每条 ToolCall 一行：能力名 · 权限档 · 入参摘要 · 结果摘要 · 成本 · 耗时 · 风险等级。
- **授权面板**：沿用 v1.5（待授权列表 + 两级确认弹窗）。
- **接管控件**：暂停 / 继续 / 注入指令 / 取消。
- **验收**：`A8`。

### F12 迁移与兼容（双轨）

- **阶段一（灰度）**：`CLIPWRIGHT_AGENT_MODE = off | shadow | on`（默认 off）。
  - `off`：老管线，行为不变；
  - `shadow`：agent 只规划**不执行**，产出计划与预估成本供对照（零副作用）；
  - `on`：agent 执行。
- **老 API 兼容**：`POST /api/pipeline/run-async` 内部转成 `Task`（当 `AGENT_MODE=on`），返回结构保持兼容。
- **退役条件**：连续两个版本灰度对比达标（质量 ≥ 基线 90%、成本增幅 ≤ 30%、失败率不升）后，老编排转 `legacy` 只读保留一个版本。
- **验收**：`A9`、`A13`。

## 7. 非功能需求

| 维度 | 要求 |
|---|---|
| 成本 | 常规选题单任务成本 ≤ v1.5 同选题的 130%；超限必须在计划阶段就能预估（计划里带 `est_cost_usd`） |
| 延迟 | 首个"可见进展"（计划或第一步开始）≤ 10s；单次工具调用超时默认 60s（可配） |
| 可用性 | Task 可中断可续跑；后端重启不丢事件流（Mongo 落盘） |
| 可测性 | 每个新模块有单测；golden runs 可在 CI 跑（无网络） |
| 安全 | 五条红线由测试断言；`dangerous` 档工具未授权调用必须失败 |
| 可移植 | 不新增必须依赖（录制/回放用本地文件，不引入新服务） |

### 8.3 退役（C7 之后）

## 11. 验收标准

| 编号 | 标准 | 检验方式 |
|---|---|---|
| A1 | 四道闸触顶后优雅收尾（有结论、有已完成产物、有未完成原因） | 构造超限任务，断言三件套齐全 |
| A2 | `record/replay` 同录制产出结构一致的 timeline | 录制一条、replay 两次，diff 归一化 timeline |
| A3 | 每次 ToolCall 都有审计（含被拒/超时/待授权） | 抽 30 条核对字段齐全 |
| A4 | 权限档生效：`dangerous` 未授权调用必须失败；`read` 不打扰用户 | 分档构造用例 |
| A5 | 预算耗尽时不再发起调用，并给出"还差什么" | 设 $0.01 预算跑一条 |
| A6 | `kill -9` 后 `resume` 不重复副作用（幂等键生效） | 检查点续跑 + 副作用计数 |
| A7 | 能力覆盖：老管线能干的活，≥90% 能由 agent 单独调用复现 | 能力矩阵逐项勾验 |
| A8 | 计划视图能回答「在干什么/为什么/花了多少/卡在哪」 | 5 人可用性测试 ≥4 通过 |
| A9 | 老 API `run-async` 在 `AGENT_MODE=on` 下仍可用且返回兼容 | 回归脚本 |
| A10 | 与 v1.5 同选题产物质量不下降（盲评 ≥ 基线 90%），成本增幅 ≤30% | 20 选题 A/B 盲评 |
| A11 | 长任务不因上下文超限失败（压缩生效） | 构造 50 步长任务 |
| A12 | 子代理星型与并发上限语义保持 | 复用 v1.5 用例 |
| A13 | `AGENT_MODE=off` 时行为与现状一致 | 逐字节比对 timeline |

## 12. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 成本失控 | 用户账单暴涨，信任崩塌 | 四道闸 + 计划里带预估成本 + 默认 `plan_only` 确认（Q6） |
| 工具面做不全就上内核 | agent 只能干"半套活"，体验比老管线更差 | C1 是硬门槛：`A7` 不过不进 C2 |

| 上下文爆炸 | 长任务失败率飙升 | 摘要压缩 + 结构化提取 + 上限硬闸 |
| 双轨长期并存 | 两套逻辑打架、维护翻倍 | C7 设退役条件，不无限期并存 |
| `dangerous` 工具面扩大 | 事故面变大 | 权限档 + 两级确认 + 「外传类一律授权」的硬规则 |
| 迁移期用户困惑 | 两套入口 | 前端只暴露新入口，老入口标为"经典模式（将下线）" |
